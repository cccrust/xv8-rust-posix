# xv8rust v0.5

**目標：在維持 `posix/tools` 全數可編譯的前提下，開始收斂警告，並把最常見的執行期缺口補起來。**

v0.4 已經把最後一批 `libc` 依賴工具解掉。v0.5 的重點不再是「再多解幾個編譯錯誤」，而是把現有可消除的警告整理乾淨，並讓 `read_link`、`spawn` 這類已經被工具使用到的能力從 stub 走向真實實作。

## 這版要做什麼

### 警告整理
- 移除 `xv8-user-std` 中可直接修正的 unused / dead code 警告
- 讓 compat crate 的保留 API 警告更乾淨
- 只保留真正來自工具原始碼、且不影響驗證結果的警告

### 執行期支援
- `fs::read_link`：從固定 `Unsupported` 改為實際 syscall 或 kernel 轉接
- `process::Command::spawn`：從 stub 改為實際建立子行程
- 延伸 `Child` / `Stdio` / `Output` 行為，讓常見命令列工具可真正跑起來

---

## 預期影響

### 直接受益的工具
- `file`
- `sh`
- `command`
- `bash`
- `man`
- `nohup`
- 以及任何會走到 `Command::spawn()` 的工具

### 可改善的體驗
- `read_link` 不再只回傳 `Unsupported`
- `spawn` 不再只是編譯期接口，至少能連到 xv8 的程序建立路徑
- 日後若補齊對應 syscall，會更容易擴展到 pipeline、重導向與背景工作

---

## 設計方向

1. **先清內部警告**
   - 優先處理我們自己加進去、且能安全消掉的 warning。
   - 不刻意去改大量工具原始碼的命名或控制流程。

2. **read_link / spawn 先打通**
   - `read_link` 先以最小可用方式接上 kernel 能力。
   - `spawn` 先以 xv8 能支持的最小流程建立 child，之後再逐步補齊 stdout/stderr/環境與 wait 行為。

3. **保持 API 相容**
   - 既有 `posix/tools` 不應該因為這版而需要大範圍改動。
   - 只在必要時做局部型別與 trait 橋接。

---

## 已知限制

- `xv8-libc-compat` 仍然是最小相容層，不是完整 POSIX `libc`
- `spawn` 即使接上 syscall，也可能先只支援基本場景
- `read_link` 的完整語意仍取決於 kernel / syscall 可用性
- 只要工具本身寫法保留大量 `#[cfg(unix)]` 分支，部分 warning 可能仍會出現

---

## 驗收方向

1. `cargo check -p tools --target riscv64gc-unknown-none-elf -q`
2. `xv8rust` 自身警告數量下降
3. `file`、`sh`、`command`、`bash` 相關流程不再停在 `Unsupported`
4. `fs::read_link` 與 `process::Command::spawn` 至少具備真實執行路徑

---

## 下一步

- 先清掉 `xv8-user-std` / `xv8-libc-compat` 內部能安全修的 warning
- 再補 `read_link`
- 最後處理 `spawn`，因為它通常牽涉到更多子行程與 stdio 邏輯
