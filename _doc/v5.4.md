# v5.4 OverlayFS (分層聯合掛載)

## 目標

在 xv8 中實作類似 Linux overlayfs 的堆疊式檔案系統，將一個唯讀層 (lowerdir) 和一個讀寫層 (upperdir) 疊加成單一目錄樹 (merged)。這是 Docker image 分層的基礎。

## 設計

### 分層模型

```
容器視角： /mnt/merged
   read-write:   /mnt/upper   (容器層)
   read-only:    /mnt/lower   (image base layer)

檔案 lookup：    upper → lower（上層優先）
新檔案建立：     寫入 upper 目錄
```

### 實作策略：Path Resolution Interception

xv8 的 FS 是 xv6-style 的 inode-based FS（無 VFS 層）。OverlayFS 採用 **path resolution interception**（路徑解析攔截）方式：

1. 在 `fs.rs::resolve_inner()` 中，每次 `Directory::lookup()` 成功後，檢查目標 inode 是否為 overlay mount point
2. 若是，將後續路徑解析委派給 `overlay::resolve_overlay_str()`
3. `resolve_overlay_str()` 在 upper 和 lower 之間進行 merged lookup（upper 優先）

```rust
// fs.rs: resolve_inner 中的 overlay hook
match Directory::lookup(&inode, &mut inner, component) {
    Ok(Some((_, next))) => {
        if let Some((up_inum, lo_inum)) = crate::overlay::find_overlay(next.inum) {
            inode.unlock_put(inner);
            next.put();
            let remaining = rest.as_str();
            return crate::overlay::resolve_overlay_str(
                up_inum, lo_inum, remaining, parent,
            );
        }
        // 正常解析繼續
    }
}
```

### 核心資料結構

pub struct OverlayMount {
    pub mount_dir_inum: u32,  // mount point 的 inode 編號

### Merged Lookup

```rust
fn overlay_lookup(upper_inum: u32, lower_inum: u32, name: &str)
    -> Result<Option<(Inode, bool)>, FsError>
```

1. 先在 upper 目錄查詢 `Directory::lookup` — 找到則回傳 `(inode, true)`
2. 再到 lower 目錄查詢 — 找到則回傳 `(inode, false)`
3. 都找不到 → 回傳 `None`

### overlay_create

當 process 在 merged view 建立新檔案時，透過 `overlay_create(path, type, major, minor)` 自動導向到 upper 目錄：

1. 使用 `overlay_resolve_parent()` 找到 parent 目錄（在 upper 中）
2. 檢查檔案是否已存在（避免重複建立）
3. 在 upper 目錄中 `Inode::alloc` + `Directory::link`

### 系統呼叫

| 編號 | 名稱 | 功能 |
|------|------|------|
| 148 | `OverlayMount` | `overlay_mount(mount_point, upper_path, lower_path)` — 建立 overlay 掛載 |
| 149 | `OverlayUmount` | `overlay_umount(mount_point)` — 卸載 overlay |

**sys_mount 流程**：
1. 解析 mount point、upper、lower 三個路徑
2. 驗證三者皆為目錄
3. 檢查 mount point 尚未被佔用
4. 將 `OverlayMount { mount_dir_inum, upper_inum, lower_inum }` 加入 mount table

**sys_umount 流程**（繞過 overlay hook）：
1. 使用 `Path::resolve_parent()` + `Directory::lookup()` 手動解析 mount point inode
2. 繞過 `resolve_inner` 中的 `find_overlay` hook（否則回傳的是 upper inode 而非 mount point inode）
3. 在 mount table 中找到對應項目並移除

### 兩個修復的 Bug

#### Bug 1：Null-termination 問題

**症狀**：`overlay_mount("/mnt/merged", "/mnt/upper", "/mnt/lower")` 回傳 `EINVAL`。

**根因**：`fetch_string()` 讀取使用者空間字串直到遇到 `\0`，但 Rust `&str` literal 在 `.rodata` 中不保證有 null terminator。`"/mnt/merged"` (11 bytes) 未對齊，會直接讀相鄰的 `.rodata` 資料，產生 ∼256 bytes 的垃圾路徑 → `FsError::Resolve`。

**修復**：在 `user/src/syscall.rs` 的 `overlay_mount()` 和 `overlay_umount()` 安全包裝函式中，使用 stack buffer (`[u8; 256]`) 拷貝路徑字串並加上 `\0` 終止符。

#### Bug 2：Umount Overlay Redirect

**症狀**：`overlay_umount("/mnt/merged")` 回傳 `EINVAL`。

**根因**：Mount 之後，`Path::resolve("/mnt/merged")` 觸發 `find_overlay` hook，回傳的是 **upper 目錄的 inode** 而非 mount point 本身的 inode。所以 `sys_umount` 在 mount table 中找不到對應項目。

**修復**：在 `sys_umount()` 中手動解析 mount point：使用 `resolve_parent()` + `Directory::lookup()` 繞過 overlay hook，確保取得 mount point 的真實 inode。

## 已知限制

1. 僅支援一層 lower（無多層疊加，Docker 需要多層）
2. 無 whiteout 支援（刪除 lower 檔案後，merged 中仍可見）
3. 無 copy-up 支援（修改 lower 檔案時不會自動拷貝到 upper）
4. 無 `O_NOATIME` 等進階 flag 處理
5. Mount table 為全域（無 mount namespace 隔離）
